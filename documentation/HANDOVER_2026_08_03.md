## 3. Load-bearing decisions — do NOT "fix" these

### 3.1 A COMPOUND SPARSE INDEX IS NOT SPARSE THE WAY YOU THINK

This is the single most important thing in this document.

MongoDB indexes a document in a compound sparse index when **AT LEAST ONE** key is
present. `realmId` is `required`. So `{realmId, X}` + `sparse: true` indexes
**every** document, including those with no `X` — as `{realmId, X: null}` — and the
second such document is rejected `E11000`.

Two indexes were affected:

- `{realmId, dedupeKey}` (new) — would have rejected every bill after the first,
  **permanently wedging Telegram bill ingest**.
- `{realmId, telegramMessageId}` (**pre-existing!**) — notices carry no
  `telegramMessageId`, so exactly ONE notice per realm could ever exist. And
  `createNotice` swallows `E11000` as "already exists", so **7 of 8 notice types
  would have been silently invisible.**

Both are now `partialFilterExpression` (`$type: 'string'` / `$type: 'number'`).
Verified against the live mongo 4.4. The old comment on the pre-existing index
("sparse so 'upload' items are exempt") was simply **false**.

**Verify the migration landed** (`syncIndexes` drops+rebuilds on boot):
```bash
# in mre-mongo-1, db mredb
db.inboxitems.getIndexes()   # both must show partialFilterExpression, sparse absent
```

### 3.2 Auto-resolution FREES the dedupeKey (`$rename` → `resolvedKey`)

A notice is otherwise immortal until the 30-day TTL: the only other
`status:'dismissed'` write is the user-driven route. And each condition fires at
several windows, so one unpaid bill accumulated 4 pending items — pay it on day 2
and the day-1/day-0 notices still claimed money was owed.

`resolveResolvedConditions` re-checks each pending notice's own entity and
dismisses stale ones. Critically it **`$rename`s `dedupeKey` → `resolvedKey`**:

- a **user**-dismissed notice KEEPS its key ("stop telling me") — deliberate;
- an **auto-resolved** one frees it, so a RETURNING condition can notify again
  (a receipt can be reversed by a corrective re-import).

Without the rename the returning condition hits `E11000` → `created:false` →
money silently invisible. Safe against the unique index because the partial
filter only indexes string `dedupeKey`s. Mutation-tested.

### 3.3 The cron has a LEADING TICK — do not remove it (`cf8a9b53`)

`startLeaseExpiryCron` originally installed only `setInterval(fn, 1h)`. Its
once-per-day guard is **module state that resets on restart**. So every deploy
pushed the day's notices an hour out, and a container restarting hourly starved
them forever. **This is why nothing had ever fired on NAS** — every scan line in
the production log read `0/0/0`. The leading tick (30s after boot) is idempotent
via the existing day guard.

### 3.4 The vacancy notice fires AFTER `building.save()`, and BEFORE the recompute

- **After save** because `Building` has `optimisticConcurrency: true` — a
  `VersionError` rolls the flip back, and notifying first would alert about a
  vacancy that never happened.
- **Before `_recomputeVacantOwnerForProperties`**, deliberately. Gating the
  notice on that rebuild would be WRONG: the rebuild is best-effort and can
  legitimately no-op, so gating would drop alerts for real vacancies. The
  comment in the code says this; don't "correct" it.

### 3.5 Other

- `unit-vacant` dedupeKey is per **UTC day**, not per month (a real
  vacant→re-let→vacant inside one month was being swallowed).
- Greek months in the digest are **GENITIVE** («Ιουλίου», not «Ιούλιος»). Known
  trap; helper at `webapps/landlord/src/utils/greekMonths.js`; the api service has
  a local copy because it can't import the landlord util.
- The bell badge counts **bills only**; notices add a dot, not a number (one bill
  fires at 4 windows → badge read 4 for a single bill).
- `notice.link` is validated before reaching an `href` (app-relative single-slash
  path only). Not reachable today, but an href is the wrong place to find out.
